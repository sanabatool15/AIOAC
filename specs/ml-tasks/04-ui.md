Task types: `classification` (built), `regression` (a number), `forecast` (numbers over time), `grouping` (clusters), `unusual` (anomaly detection). ## 0. Principles

1. One seam. Every number about a model goes through ONE pure module, `frontend/lib/task.ts` (new), keyed by a `TaskType`. Screens never branch on the type themselves; they call `describeBaseline(p)`, `targetControl(p)`, `describeForecast(p)`, `describeResult(...)`, `describePrediction(...)` and render the plain strings and numbers they return. Classification output of these functions must equal today's strings byte for byte (golden unit tests, section 6).
2. Plain language. No F1, precision, MAE, R2, RMSE, silhouette, contamination, "train/test split", instance names. Rates stay "N out of 100". Errors are "typically off by about X". Every estimate is labelled (existing `EstimateNote`, `components/ui/estimate-note.tsx`).
3. Two kinds of numbers, never mixed. Ledger money is whole cents and only goes through `dollars()` (`lib/adapters.ts:20`). A data value (a house price, units sold) is in the data's own unit and only goes through the new `formatValue()` in `lib/units.ts`. A card never shows both without a heading that says which is which (section 4.4).
4. Safe fallback. A missing `task_type` means `classification` (old servers). An unknown string is NOT classification: it shows a generic "This kind of problem is newer than this page" card, the receipt, and no score numbers.
5. No target, no price promise where there is nothing to verify (grouping, unusual): the UI shows no "Target reached/not reached", no forecast, and no success fee line, only what the server sends (inferred: owner question 1 in `specs/regression-and-task-types.md`).

### 2.1 Task-type chip and correction (new `TaskTypeChip`, `components/shell/task-type-chip.tsx`)

Where: top of `ProjectPanel` (above `JourneyCard`, `project-panel.tsx:70-71`), in the `Overview` header (`project-detail.tsx:131`), and echoed in the first assistant message through a `choices` block.

Chip: a small tag, "Kind of problem: Predict a number" plus a text button "Change". Render nothing when `task_type` is absent (old server) or null (not decided yet; the agent is still asking).

| `task_type` | Chip label | One-line example (shown in the dialog) |
|---|---|---|
| classification | Pick an answer | "Will this customer leave? Yes or no, or one of a few groups." |
| regression | Predict a number | "What will this house sell for? An amount or a score." |
| forecast | Predict numbers over time | "How many orders next month? What comes next in a series." |
| grouping | Find groups | "Which kinds of customers do I have? No right answer, just groups." |
| unusual | Find unusual records | "Which transactions look odd? No right answer, just the odd ones." |

Change dialog (`Modal`, `components/ui/modal.tsx`): title "What kind of problem is this?", a radio group of the five rows above (name and example, each a full-width 48 px label), buttons "Use this" and "Cancel". Helper text: "Changing this restarts the free steps. Nothing is charged." When the project has a quote, a hold, a run or status past `baseline_done` (inferred rule, server enforces with 409): the "Change" button is replaced by plain text "Locked once a price is set" and an `aria-describedby` explanation. The dialog returns focus to "Change". On 409 the dialog shows the server's plain message in `ErrorLine`.

API (inferred): `POST /projects/{id}/task-type` body `{task_type}` -> 200 `{task_type, status}`; free; resets readiness/baseline/forecast. Frontend: `api-real.ts` `setTaskType(id, t)`.

States: loading (button disabled, "Changing..."), error (inline), empty (no chip). A11y: chip is `<p>` with `aria-label="Kind of problem"`; the dialog uses the existing modal focus trap; radios are native inputs.

## 4. API adapter changes

### 4.1 Types (`lib/api.ts`) (all inferred)

```ts
export type TaskType = "classification" | "regression" | "forecast" | "grouping" | "unusual";
export interface ValueUnit { kind: "currency" | "count" | "percent" | "measure" | "unknown"; code?: string | null; label?: string | null }
// BProject gains:
task_type?: string | null;         // absent or null: read as "classification"
value_unit?: ValueUnit | null;     // unit of the answer column, regression and forecast only
// baseline becomes a union keyed by score_kind (absent = classification):
type BBaseline =
 | { score_kind?: "classification"; accuracy: number; simple_guess_accuracy: number }
 | { score_kind: "regression" | "forecast"; typical_error: number; simple_guess_error: number; closeness: number;
     error_curve?: { score: number; error: number }[]; horizons?: { steps: number; label: string }[]; test_label?: string }
 | { score_kind: "grouping"; n_groups: number; groups: BGroup[]; separation?: "clear"|"mixed"|"weak" }
 | { score_kind: "unusual"; flagged_count: number; flagged_share: number; top: BUnusualRow[] };
```

`BForecast` adds `kind?`, `predicted_error?`, `error_low?`, `error_high?` (data units, low = better end), keeping `predicted_metric` and band as 0..1 closeness for the existing maths. `BTraining.result.verification` becomes `{kind?, value, target, passed, value_error?, target_error?}`; `result` gains `groups?`, `flagged?`. `BModel` (available) gains `score_kind?`, `typical_error?`, `simple_guess_error?`, `groups?`, `horizons?`, `value_unit?`; `BPredict` gains `interval?`, `typical_error?`, `group?`, `unusual?: {flag: boolean; score: number}`, `series?`. All new keys optional so today's server and fixtures still type-check.

### 4.2 Adapters (`lib/adapters.ts`, new `lib/task.ts`, new `lib/units.ts`)

- `taskTypeOf(p)`: returns a `TaskType`, or `"unknown"` for an unrecognised string; `null`/`undefined`/`""` -> `"classification"`. The only place the fallback exists. Unit-tested with all five values, null, undefined and `"surprise"`.
- `toBaseline` returns the union; screens use `describeBaseline`. The existing `BaselineView` shape is kept for C so `journey-card.tsx:26` and `project-detail.tsx:151` keep compiling until moved.
- `toForecast` keeps `target/expected/low/high/confidence` as closeness percent (the same 0..1 maths as today) and adds `expectedError/lowError/highError` as `FormattedValue` strings when present.
- Rates: 0..1 to percent stays `percent()`. Closeness is 0..1 server side, shown "N out of 100".
- Cents/dollars: untouched. The data-value formatter must never receive a `_cents` field.

### 4.3 Null handling

Every new field is optional. `formatValue(null | undefined | NaN | Infinity)` returns "—". A sentence is built only when all its numbers are present (`describeBaseline` returns `{sentence: null}` otherwise and the card shows "No result yet."). Lists default to `[]`. Arrays and strings from the server are length-cut. `fileSize`, `sklearnNote` and `toPublic` get explicit null guards (audit 8).

### 4.4 Units and currency label (`lib/units.ts`)

How the label is chosen: the SERVER decides (`value_unit`), from the column name and values, and the user confirms or corrects it in the task chip dialog for R/F ("Your answers are in: Dollars / A count / Percent / Something else (name it)"; inferred route `POST /projects/{id}/task-type` accepts `value_unit`). The frontend never guesses a currency from a column name.

`formatValue(v, unit)`:
- `currency` with ISO `code` ("USD", "EUR"): `Intl.NumberFormat("en-US", {style: "currency", currency: code, maximumFractionDigits: 0|2})`. An invalid code (not `/^[A-Z]{3}$/` or rejected by Intl) falls back to the unknown format. The component never writes `$` by hand.
- `percent`: "12.5%" (value already in percent points as the data holds it; the server states the scale).
- `count`: integer with thousands separators and no symbol.
- `measure` and `unknown`: plain number with separators, no symbol; the card adds the sentence "in the same units as your "{target}" column" once. `measure` with a `label` ("kg", "minutes") appends it after the number, label trimmed to 12 characters and rendered as text.
- Precision: 3 significant figures for errors and predictions below 1,000; 0 decimals at or above 1,000; compact form (1.2M, 3.4k) above 1,000,000 with the full number in `title` and `aria-label`. Typical error is `Math.abs`; never negative. `-0` prints "0".
- Untrusted text: `label` and group names come from dataset content. Render as React text only, cut to the stated lengths, strip control characters, never pass to `dangerouslySetInnerHTML` or the markdown reader.
- Safety against confusion with ledger money: a data currency value is always inside a sentence that names it ("typically off by about $4,200"), never in a `dl` row next to "Compute" or "Held". Cards that show both (quote step after a forecast card) are separate `Card`s with different headings, and the data card carries the text "These are in your data's own units. They are not charges."
- Guard test: components may not call `Intl.NumberFormat`, `toLocaleString` with `style`, or contain a `$` literal followed by an expression; only `lib/units.ts` and `lib/adapters.ts:dollars` may.

## 8. Risks

- The API fields in section 4 are guesses. If backend names differ, only `lib/api.ts` and `lib/task.ts` change (this is why the seam exists).
- Closeness slider: the server's `error_curve` is an estimate; a coarse curve can make the caption jumpy. Interpolation is linear and clamped, and the caption says "(an estimate)".
- "N out of 100" for a non-count (closeness) can be read as "N percent of my predictions right" (the risk named in `regression-and-task-types.md` 2.2). Mitigation: it always sits next to "typically off by about X" and the word "closeness".
- Data currency next to ledger dollars can be mistaken for charges (section 4.4 mitigations).
- Group names and unit labels are dataset-derived text (prompt-injection or HTML risk): text-only, length-cut, tested.
- Public page for G/U could leak records: allow-list counts and shares only; HUMAN REVIEW.
- Grouping and unusual may be un-sellable (owner question 1); slice 8 then shrinks to read-only results.
- Recharts band and dashed series add bundle weight and a11y work; the table fallback is mandatory.
- `ReactiveFake` per-keyword case selection is test-only but must stay out of `app/` (architecture test).
- Phone layout of the two-bar and group cards is unverified until slice 9.
